# ADR 0001 — 以「AI 主用的能力面」为产品主语，而非「人用的凭据后台」

- **状态**：已接受（2026-10-26）
- **决策者**：平台负责人
- **相关**：`docs/credvault-ai-first-review.md`（v0.2 复盘）、`docs/credvault-design.md`（v0.1，部分条款被本 ADR 取代）

## 背景

现有资产 `cred_broker`（2487 行）已具备策略引擎、哈希链审计、业务失败判定、令牌生命周期，
并在跳板机跑通。做「产品化」时出现两条路：

- **A 人用平台**：补人类 RBAC、五页控制台、多租户、轮换/分发 UI —— 直觉上「像个产品」。
- **B AI 能力面**：补能力注册表、server instructions、返回体预算、自省工具、异步审批 ——
  直觉上「不像产品」，因为它没有多少页面。

实测参照物（Sigil 2.4.0 deb 静态取证）显示：**它 80% 的工程投入在 AI 面**
（`initialize.instructions` 60 行提示词、`vault_capabilities` 一表一工具、
`mcp_tokens` 双轴 + IP 白名单、会话级审批豁免、只读自省工具组），页面只占很小一块。
同时它要求桌面端常开+解锁才有 MCP —— 这恰是我们在服务器场景的**优势而非差距**。

## 决策

采用 **B**。产品主语是「AI 能不能自己把活干完」，人只在**审批 / 审计 / 令牌**三处出现。

推论：
1. 不做凭据 CRUD 后台、不做仪表盘、不做多租户 —— 省下的时间全部投到能力面。
2. UI 只保留三视图；审批必须能在浏览器点完，**不要求人会命令行**。
3. 授权对象从「URL+method」升级为「能力名」——因为 URL 白名单表达不了语义动作
   （放行 `/api_jsonrpc.php` 后 AI 仍可发 `host.delete`）。
4. 轮换不做「全自动改所有上游」，只做「生成 → 落库（带历史）→ 探针验证 → 失败回滚」，
   远端投放交给能力（可审计、可审批）。

## 被否的备选

| 备选 | 否决理由 |
|---|---|
| 采用 RuoYi 底座（Spring Boot + Vue + MySQL + Redis） | 违反「单产物、零外部中间件、离线可装」；只借其权限模型，不借技术栈 |
| 依赖官方 `mcp` SDK | 1.x/2.x API 分裂（FastMCP vs MCPServer、host/port 传参不同），部署反复踩版本坑；手写 JSON-RPC 约 200 行换取零版本依赖 |
| 复刻 Sigil 的桌面金库形态 | 必须 GUI 常开+解锁，服务器/容器不成立；我们已在无头这一点领先 |
| 继续用「通用 HTTP 代理 + URL 白名单」当 AI 接口 | 语义缺失：AI 要自己知道每个上游的报文形态，错误率高、token 贵、权限收不住 |

## 后果

**正面**
- 新增一个上游 = 加一段 YAML，零代码零发版；这是「交付到别人服务器能直接用」的前提。
- 工具列表按双轴授权**渐进披露**，未授权能力根本不出现，既省上下文又减误调用。
- 返回体有预算与结构化裁剪，单次调用成本可控。
- 审批不再阻塞无人值守任务（异步 + 轮询 + 会话豁免 + 事件推送）。

**负面 / 代价**
- 能力描述由人写，写不好 AI 就选错工具 —— 质量前移到 YAML，需要 review 习惯。
- `kind: rotate` 的探针覆盖率取决于是否有人声明 `probe`；没声明就只验证「能落库」。
- 三视图对「想点点鼠标改凭据」的用户不够友好，故意为之。

**何时重新评估**
- 出现多组织共用需求（那才谈多租户）；
- 能力数超过 ~200 且出现命名/归类混乱（那时需要 namespace 与检索）；
- 出现对「人用后台」的明确付费诉求。
